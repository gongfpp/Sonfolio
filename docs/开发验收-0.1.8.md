# 声迹 0.1.8 可靠性改进记录

本轮依据用户 2026-09-13 提供的审阅意见，优先修复录音异常可见性、持续缺口和摘要分类的正确性，版本为 0.1.8 / versionCode 9。录音增加 Android `AudioRecordingCallback` 与 `isClientSilenced` 监测，音量条取自实际 PCM 均方根能量，不再用固定循环动画冒充输入强弱；界面区分服务启动、持续写入、系统静音、超过两秒未见写入更新和输入设备切换。零音量本身不等于系统静音或故障，只有系统明确报告静音才记录此类缺口。实现依据 [Android 共享音频输入说明](https://developer.android.com/media/platform/sharing-audio-input) 与 [AudioRecord 回调接口](https://developer.android.com/reference/android/media/AudioRecord)。

录音缺口改为可持续的区间，Schema 3 允许 `endedAtMillis` 为空并增加 `kind` 区分设备中断和系统静音。异常退出、恢复旧文件或者再次启动失败都不能把“查看了现场”当作“已经恢复录音”，缺口保持开放，只有重新写入非系统静音的音频才闭合；重复失败不会新增一串固定一秒的记录。原音仍保留，包括被系统静音时写入的原文件；首页对开放缺口显示“等待恢复”，日统计计算至当前时刻。可用空间低于 512 MB 时提示，低于 64 MB 时停止录音、收尾并保留原音，不自动删除数据。

已知缺口参与对话合并边界，故障前后短于两分钟的语音不再仅凭时间接近合并。给已有会话新增缺口而拆分时，第一组保留原 ID，其余组使用不同 ID，避免多个分组重复使用旧 ID 覆盖彼此；这不等于已实现补处理时多场会话合并的旧 ID 重定向。总结输入和指纹携带相关缺口，提示模型说明记录不完整、不能推断缺失内容；基础一日回顾也注明此限制，播放器对已知缺口显示提示，仍允许回听保留的完整原文件。疑问、否定和条件句保留在普通要点或问题中，不再直接归类为决定与后续事项，短对话生成的非空结构化字段也能显示。

VAD/ASR 客户端串行持有推理连接，完成、取消和超时后解绑；服务销毁时只终止自身 `:inference` 进程，客户端等待 Binder 死亡通知。如果五秒内未确认退出，就保留退出信号，在确认之前阻止下一项连接，同时保留原本的超时或取消结果，不用清理阶段的异常覆盖它。这样不再把 `HandlerThread.quitSafely()` 误当成中止正在执行的 native 调用；独立进程隔离不代表整机低内存时绝不会回收录音进程，全天录音和历史数据增长压测仍属于后续验收。

本机 NDK 29.0.14206865 原安装缺少 CMake 元数据、clang 入口和 lld 链接器，9 月 13 日将官方归档中缺失的必要文件恢复到固定 SDK 安装路径，不再依赖临时 NDK 副本。可审查的修复脚本为 `scripts/repair-ndk-r29.mjs`，只恢复已验证版本目录中不存在的目标文件，使用受限 HTTP Range、ZIP CRC 校验与 56 MB 下载上限，不获取整个约 1 GB 的 NDK 归档，也不下载 AI 模型。正常工程构建直接在 `android/` 运行 `./gradlew --no-daemon --no-watch-fs -Pkotlin.compiler.execution.strategy=in-process :app:assembleDebug :app:assembleDebugAndroidTest :app:testDebugUnitTest :app:lintDebug`，无需指定临时 Gradle 或 NDK 路径；生成式总结运行时仍固定源码与归档摘要。

9 月 13 日已在正常 SDK 路径成功构建 Debug APK 与 Android 测试 APK，最终补丁的 40 项 JVM 测试全部通过，Lint 为 0 errors / 18 warnings；警告主要涉及依赖更新、仅 arm64 支持、备份配置和空间 API 提示，不应写成“没有警告”。最终 APK 已覆盖安装到 Redmi Note 8 Pro / Android 10，包管理器确认版本 0.1.8 / code 9，手机 `base.apk` 与本机产物 SHA-256 均为 `5cb5488846a33a442436f62d50745d8a90d9b6c62524d6f75732f94d70c6d95d`。本机产物位于 `android/app/build/outputs/apk/debug/app-debug.apk`，大小 262,789,271 字节，没有额外下载本地总结模型。

最终 APK 的 11 项真机集成测试在 24.551 秒内通过，范围为 `SummaryIntegrationTest` 六项、`RecordingGapIntegrationTest` 两项，以及 `PipelineIntegrationTest` 的原音修复、模型超时与外部取消、本地 VAD/ASR 处理三项。它们验证了设置确认与密钥加密、模拟 HTTPS 失败、结构化解析和缓存失效、Schema 1→3 与 2→3 迁移、坏 GGUF 在独立进程失败返回、开放缺口持续十分钟及去重、插入缺口后稳定拆分 ID、WAV 修复使用真实样本时长、ASR 超时不冒充外部取消，以及真实 Silero/SenseVoice 调用不修改固定样例文件。十分钟缺口由测试时间戳构造，不是十分钟真机故障观察；模型样例为短静音音频，不能证明嘈杂中文的识别准确率，坏 GGUF 失败也不能证明有效模型能成功总结。首次迁移测试曾因测试夹具假定 Schema JSON 总有 `indices` 字段失败，改为兼容省略该字段后，单项及最终整组均通过。

升级前从真机保存了元数据临时副本并计算全部 11 份 WAV 的 SHA-256；实际用户库由 Schema 1 升到 3，SQLite `quick_check` 返回 `ok`，保留 11 个原音条目、77 条转写、6 场对话和 2 条已有缺口。升级后比对原音条目、转写和标记的原有数据库行，没有发现丢失或修改；最终安装及集成测试结束后，再次核对 11 份原音校验和全部一致，数据数量和完整性检查仍相同。本轮没有新增正式录音，没有删除用户原音，也没有将用户转写送到外部服务；测试数据库和固定音频均与用户记录隔离，退出时清理。

真机首页曾成功打开，但此次手工录音与麦克风竞争测试没有完成：手机存在另一组持续界面操作，前台反复切走；测试采集页还因 MIUI 将测试包 `RECORD_AUDIO` 的 AppOps 设为 `ignore` 而初始化失败，不能仅归因于界面切换。测试页现已增加窗口获得焦点后启动、权限和初始化状态检查、失败提示，以及离开页面释放麦克风，但尚未在允许权限的独占测试条件下重验。没有擅自修改系统隐私权限或锁屏设置，不能以此宣称系统静音监测、输入设备切换、锁屏长录音或缺口自动闭合已经实机通过；麦克风竞争页面仅存在于测试 APK，样本不保存、不上传，不进入主 APK。

后续按审阅顺序推进：首先把全量重建改为受影响会话和日期的增量更新、文本计算移出写事务，并将采集循环与数据库等待隔离；再建立合并会话的旧 ID 映射，确保详情、搜索锚点和摘要能迁移。之后补原音批量管理、完整备份恢复、历史标记和手动标题、摘要引用来源，以及自动总结请求合并和模型复用；最后调整总结配置入口、拆分页面与播放器代码、优化组合搜索和回听效率。本轮不宣称这些已完成，也不宣称真实本地生成式总结、全天锁屏、低存储实机故障和大历史数据压测已经验收。
